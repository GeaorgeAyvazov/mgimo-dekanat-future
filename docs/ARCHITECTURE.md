# Как устроен прототип

Приложение: React 19 + TypeScript, Vinext/Vite, Cloudflare Worker и D1 (SQLite). Интерфейс, API и база составляют один проект. Компоненты интерфейса получают только данные вошедшего пользователя; исходные учебные записи импортируются только сервером. Внешних ИИ API и ключей в продукте нет.

## Вход и разграничение

Три заранее заведённые вымышленные записи: два студента и сотрудник. Пароль каждого аккаунта проверяется через bcrypt (cost 12); в таблице `users` хранится хеш, а не пароль. Открытый тестовый пароль опубликован намеренно, исключительно для демонстрационных аккаунтов. В реальной эксплуатации их нужно удалить, подключить университетский SSO и управляемое создание сотрудников.

После входа сервер создаёт случайный 256-битный токен. В D1 хранится его SHA-256, в браузере — HttpOnly cookie, с SameSite=Lax и Secure на HTTPS. Срок сессии — 8 часов. Выход удаляет серверную сессию и cookie. Токен не помещается в localStorage. Ответы API и файлы помечаются `no-store`.

У API нет параметра «чей профиль показать». Профиль, расписание и оценки определяются сессией. Каждая студенческая заявка и скачивание PDF выбираются SQL-запросом одновременно по `id` и `owner_id`. Подстановка чужого адреса даёт 404. Сотрудник может видеть все обращения по своей роли; право менять статус проверяется сервером. Роль из запроса или браузера не принимается.

Записи используют параметризованные SQL-запросы. Запросы изменения проверяют Origin, JSON Content-Type и специальный заголовок. Есть серверная проверка полей, размер тела ограничен, повторная отправка формы защищена уникальным ключом `(owner_id, idempotency_key)`. Неверный вход ограничен десятью попытками на сочетание IP и логина за 15 минут. Это базовая защита прототипа, не полноценный независимый аудит безопасности.

## Жизненный цикл заявки

`Заявка принята → В работе → Готово`. У бумажной справки есть отдельный переход `К выдаче → Выдано` с датой в истории.

Сотрудник может запросить уточнение (`Нужен ваш ответ`). После ответа студента заявка возвращается в работу. Сотрудник указывает причину отмены. Студент может подтвердить отмену собственной заявки до начала обработки. Обновление проверяет ожидаемый статус и сохраняет событие вместе с изменением в транзакции. При конфликте ответа студента сервер возвращает 409, а клиент сохраняет введённый текст в форме.

Электронная справка об обучении на русском или английском формируется сразу. Остальные виды справок и бумажный вариант обрабатывает сотрудник. Срок — три рабочих дня без выходных, без учёта производственного календаря: для промышленной версии нужен календарь праздников и правила филиала. Значимые события заявки попадают в личную ленту уведомлений. Кабинет обновляет данные в активной вкладке раз в 30 секунд, при возвращении в неё и открытии уведомлений. Карточку можно обновить отдельно. Email, SMS и push не подключены.

## Документы и хранение

D1 хранит пользователей, сессии, заявки, события, прочитанность уведомлений и ограничения входа. Схема создаётся миграцией Drizzle, не обработчиками запросов. Отдельный серверный seed выполняет только идемпотентные INSERT демонстрационных данных. Существующие записи и заявки не сбрасываются при перезапуске.

Новые PDF создаются из записи владельца при готовности заявки. Кириллица встроена шрифтом DejaVu Sans с лицензией в `licenses/`. Web Crypto и PKIjs подписывают исходные байты, используя отдельный CMS и самоподписанный сертификат RSA/SHA-256. Ключ генерируется в памяти серверного процесса. Миграция 0002 добавляет таблицу неизменяемых комплектов PDF и SIG с датой и хешами. Старые готовые заявки получают комплект при первом скачивании по дате события готовности.

Владелец скачивает обе части комплекта через ту же проверку доступа. Сверка в браузере вычисляет хеши локальных файлов и сравнивает их с записью заявки. Для юридически значимого выпуска нужны доверенный сертификат вуза, регламент, интеграция с источником данных и контур подписания.

Миграция 0003 связывает сообщение о проблеме с исходной заявкой. Сервер проверяет владельца исходной заявки до записи связи. Учебный координатор получает сообщение в общей очереди. Отчёт доступен сотруднику и считает агрегаты по сохранённым событиям готовности и выдачи. CSV содержит итоги без имён студентов.

## Масштабирование и адаптация

Workers обслуживают запросы без постоянного процесса Node, D1 сохраняет данные между развёртываниями. Прототип ориентирован на небольшой пилот; нагрузочное тестирование не проводилось. Для большого вуза нужны серверная пагинация, индексы очередей, мониторинг, резервное копирование, аудит действий и оценка требований к месту хранения персональных данных.

Каталог услуг выделен в `lib/catalog.ts`, миграции — `drizzle/`, правила — `lib/server.ts`, демонстрационные данные — `lib/demo-data.ts`. Для реального филиала необходимо уточнить названия подразделений, услуги, точки выдачи, сроки и права сотрудников. Указанные кабинеты и контакты вымышлены.

## Дополнение: сервисный центр

Миграция 0001 добавляет личное избранное и поля вопроса (тема, текст, подразделение). Тема сопоставляется подразделению на сервере. У вопроса отдельная форма; завершение требует содержательного ответа сотрудника. PDF-роут для такого обращения закрыт. Избранное выбирается и изменяется только по user_id из сессии. Архив документов строится из собственных завершённых заявок. Подбор услуги - явные правила, без внешней модели ИИ.


## Справочник и карта

Профессиональный демосправочник выдаётся через авторизованный GET /api/portal/employees. Личные сведения студента в него не добавляются. Обращение из карточки задаёт тему, а сервер определяет подразделение. Карта - статические инертные SVG и минимальный JSON на том же домене; произвольные SVG не принимаются, скрипты источника не исполняются. Нажатая пара передаёт явный floorKey:roomId. Камера, поиск и выделение выполняются клиентом. Общий кампус и этажи работают без внешнего iframe или ключа картографического сервиса.
